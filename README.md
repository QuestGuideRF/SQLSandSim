# SQLSandSim

`SQLSandSim` — это демонстрация симуляции песка, в которой основная логика физики и хранение состояния реализованы на стороне `PostgreSQL`, а веб-интерфейс используется для управления и визуализации. Проект показывает, как можно выполнять шаги симуляции, хранить историю кадров и отрисовывать состояние через обычное клиент-серверное приложение.

## ✨ Возможности

- Выполнение симуляции песка на стороне базы данных `PostgreSQL`.
- Инициализация сетки симуляции с параметрами ширины, высоты и глубины истории.
- Запуск и остановка расчета через веб-интерфейс.
- Добавление областей песка и твердых блоков мышью.
- Просмотр текущего состояния симуляции через HTTP API и `WebSocket`.
- Перемотка по истории кадров с помощью таймлайна.

## 🛠 Использование

После запуска откройте в браузере `http://localhost:3000`.

В интерфейсе доступны следующие действия:

- `init` — инициализирует симуляцию с параметрами `256x144` и `keepFrames=900`.
- `start` — запускает выполнение шагов симуляции.
- `stop` — останавливает симуляцию.
- Левый клик по холсту — добавляет песок.
- Правый клик по холсту — добавляет твердый блок.
- `timeline` и кнопка `go` — позволяют перейти к сохраненному тику из истории.
- Поле `brush` — задает размер кисти в диапазоне от `1` до `80`.

### HTTP API

Сервер содержит следующие маршруты:

- `POST /api/init`
- `POST /api/start`
- `POST /api/stop`
- `GET /api/status`
- `GET /api/state`
- `POST /api/sand`
- `POST /api/solid`
- `GET /api/history`
- `POST /api/rewind`

Примеры запросов:

```bash
curl -X POST http://localhost:3000/api/init ^
  -H "Content-Type: application/json" ^
  -d "{\"w\":256,\"h\":144,\"keepFrames\":900}"
```

```bash
curl -X POST http://localhost:3000/api/sand ^
  -H "Content-Type: application/json" ^
  -d "{\"x\":10,\"y\":10,\"w\":20,\"h\":12}"
```

```bash
curl http://localhost:3000/api/status
```

```bash
curl -X POST http://localhost:3000/api/rewind ^
  -H "Content-Type: application/json" ^
  -d "{\"tick\":100}"
```

### WebSocket

После подключения клиент открывает `WebSocket` на адрес текущего хоста и получает сообщения:

- `hello` — подтверждение подключения.
- `state` — текущее состояние симуляции.
- `error` — ошибка на стороне сервера или базы данных.

## ⚙️ Как это устроено

Проект выглядит как обычная симуляция песка, но его ключевая особенность в том, что расчет выполняется в реальном времени почти полностью средствами `SQL`. В базе данных находятся физика, состояние мира, история кадров и логика обновления, а веб-приложение нужно только для управления, отображения и доставки новых состояний клиенту.

### Представление мира

Наивный способ хранить двумерную сетку в `PostgreSQL` — завести таблицу ячеек с координатами `x`, `y` и состоянием каждой клетки. Для симуляции это оказалось бы слишком дорогим вариантом: даже поле размером `256x144` содержит более `36 000` ячеек, а частые мелкие обновления по строкам плохо подходят реляционной базе данных.

Поэтому в проекте используется побитовое представление:

- один `BIGINT` хранит `64` ячейки по горизонтали;
- строка мира хранится как массив `BIGINT`;
- весь мир хранится как массив строк;
- в таблице `sim_state` поддерживается одно актуальное состояние симуляции.

Для ширины `256` требуется `4` значения `BIGINT` на строку. Высота `144` означает `144` строк состояния. Такой подход позволяет выполнять массовые обновления через битовые операции вместо большого числа точечных изменений по отдельным строкам таблицы.

### Как проходит тик симуляции

Каждый тик блокирует текущее состояние, обновляет массивы в функции базы данных и затем записывает результат обратно одним обновлением. Внутри шага симуляции логика построена как последовательность проходов:

- вертикальное падение под действием гравитации;
- диагональное движение вокруг препятствий;
- боковое растекание для заполнения пустот;
- дополнительные микро-проходы по поверхности для более естественного поведения песка.

На каждом этапе сначала вычисляются маски возможных перемещений, затем применяются побитовые преобразования, после чего обновляются маски пустых клеток. Это уменьшает количество повторных полных проходов по сетке и делает стоимость тика более стабильной.

### Импульс и выравнивание поверхности

Чтобы песок не выглядел слишком "роботизированным", в проект добавлены дополнительные механики:

- `mom_l` — сетка импульса для частиц, которые предпочитают двигаться влево;
- `mom_r` — сетка импульса для частиц, которые предпочитают двигаться вправо;
- случайное затухание импульса, чтобы направление не закреплялось навсегда.

Такой подход позволяет частицам продолжать движение в уже выбранную сторону и делает поведение ближе к сыпучему материалу. Для сглаживания рваной поверхности используются дополнительные боковые проходы только по верхнему слою, который визуально влияет на картину сильнее всего.

### Почему здесь нужен Node.js

`PostgreSQL` хорошо справляется с транзакциями и пакетными операциями, но не предназначен для постоянного игрового цикла. Поэтому в проекте обязанности разделены:

- `PostgreSQL` хранит состояние и выполняет функцию `sim_step()`;
- `Node.js` запускает бесконечный цикл с таймером;
- веб-сервер публикует новое состояние через `WebSocket` и HTTP API;
- клиент только отображает результат и отправляет команды пользователя.

Такое разделение позволяет оставить модель симуляции детерминированной и при этом получить стабильные обновления в реальном времени.

### История и перемотка

Проект поддерживает простую перемотку по кадрам. Для этого после тика состояние песка сохраняется в таблицу `sim_frame`, а текущее активное состояние продолжает храниться в `sim_state`. При перемотке выбранный исторический кадр копируется обратно в основное состояние.

Чтобы история не росла бесконечно, используется окно хранения `keepFrames`: кадры старше `tick - keepFrames` удаляются. По сути это кольцевой буфер на уровне базы данных. Перемотка рассчитана на использование после остановки симуляции, что помогает избежать конфликтов между историческим восстановлением и текущим расчетом.
